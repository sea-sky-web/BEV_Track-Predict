# 评审验证协议

> 被 `~/.claude/CLAUDE.md` 引用。此协议的目标：确保用户 **真正理解** 变更内容，而非形式化通过。

---

## 核心原则

评审不是"用户说同意就通过"。AI 必须通过 **反问验证** 确认用户理解了变更的逻辑和影响。

---

## 方案评审阶段的验证方法

### 第一步：展示方案并要求审阅

展示完整方案后，附带以下提示：

```
⛔ 请审阅以上方案。审阅后请回复你的评审意见（同意 / 需要修改 / 拒绝），
并说明理由。
```

### 第二步：反问验证（核心机制）

无论用户回复什么（包括看似详细的回复），AI **必须** 至少提出 1-2 个针对性问题来验证理解：

**验证方向（根据变更内容选择）：**

- **逻辑理解**："这次改动把 X 的处理方式从 A 改为 B，你能说说为什么 B 比 A 更适合当前场景吗？"
- **影响范围**："这个改动会影响到 Y 模块的 Z 行为，你确认这是你预期的吗？具体会怎么影响？"
- **边界情况**："如果输入是 [边界值]，改动后的行为会是什么？这符合你的预期吗？"
- **回退预案**（高风险）："如果上线后发现问题，你打算怎么回退？"

### 第三步：判定是否通过

**通过条件**：用户的回答表明他 **确实理解了变更的逻辑和影响**，即使表述不够专业。

**不通过条件**（需要继续追问）：
- 回答与变更内容无关或答非所问
- 回答完全重复 AI 方案中的原话（鹦鹉学舌）
- 回答明显表明未理解关键逻辑（如把 A 说成 B）
- 表达不耐烦并要求跳过（"别问了直接改"）→ **必须坚持，附带解释为什么这一步重要**

---

## 变更审阅阶段的验证方法

### 展示变更时

```
⛔ 以上是所有代码变更及 AI 自审报告。请逐一审阅：
1. 是否有需要修改的地方？
2. 请为你认可的变更添加批注（简要说明你的理解或确认理由）。
未经你的批注，我不会执行提交。
```

### 批注要求

- **低风险**：整体一句批注即可（如"文档修正，确认"）
- **中风险**：对关键变更点批注（如"getUserById 改为批量查询，减少 N+1，确认"）
- **高风险**：对每个文件的变更批注

**不接受的批注**：
- 空白或仅标点
- "同意"、"OK"、"没问题"等不含具体内容的确认
- 与变更内容明显无关的文字

---

## 遇到用户抵触时的话术

如果用户表现出不耐烦或要求跳过评审：

```
我理解这个流程有些繁琐，但这是你设定的全局红线规则——
目的是确保你对代码库保持掌控力，避免积累技术债务。
这个评审不需要很长时间，我只需要确认你理解了核心改动点。
我们继续：[具体的验证问题]
```

**绝对不可以**因为用户催促而跳过评审。如果用户坚持要求跳过，应明确告知：
"根据你的全局规范，评审是红线要求，我无法跳过。如果你希望修改这个规则，请直接编辑 ~/.claude/CLAUDE.md。"
